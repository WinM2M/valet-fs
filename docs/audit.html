What a full audit of our own code found

27 October 2026 · Youngjune Kwon

A tool that asks you to keep your API keys in it should be able to say what it is defending against, what it got wrong, and how you can check. This page is that. It covers an audit of ValetFS v0.1.9 (f8fba82) begun on 8 September 2026, which produced fourteen findings — four of them critical.

Fourteen findings, one root

The findings looked unrelated until they were laid out together. Then the shape was obvious: authentication was entirely "do you know the session ID". There was no code anywhere that verified the identity of the controller — the phone holding the secrets. F1, F2b, F4 and F7 are all the same hole wearing different clothes.

That is the comparison worth making against the usual arrangement. A .env file has a simple threat model: anything that can read the disk wins. ValetFS set out to remove the resting copy, and for a while it replaced "can read the disk" with "knows a session ID", which is better but not by as much as the design implied.

Where the tests are

Several findings were attack shapes rather than bugs, so the fixes carry tests that describe the attack. The repository has 23 Go test files; the ones that matter here are internal/noise/conformance_test.go (handshake conformance), internal/session/transcript_test.go and internal/session/authorized_test.go (session binding and authorisation), internal/hub/relay_test.go (what the relay will and will not forward), and internal/hardening/hardening_linux_test.go.

Release integrity

F11 closed with a SHA256SUMS file covering every artefact, cosign keyless signing, and build provenance. The installer verifies the checksum fail-closed. When cosign is not present it says so plainly rather than implying a check it did not make — a checksum that travelled from the same place as the binary is not a defence against a tampered release. Setting VALETFS_REQUIRE_SIGNATURE=1 turns that into a hard failure.

The limit is worth stating: keyless signing binds to a workflow identity, so an attacker who can change the release workflow can produce signatures that verify.

What this audit is not

It was not independent. It was a line-by-line review conducted by the author, in a working session, with an AI assistant — not a third-party penetration test and not a commissioned security review. ValetFS has had neither.

So read this page as what it is: the findings are specific, the commits are public and you can read them, and the claim "fourteen findings, four critical, all closed" is checkable by anyone who clones the repository. The claim "this code is secure" is not made here, because nobody outside the project has tried to break it yet.
