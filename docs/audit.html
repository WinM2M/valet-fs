What a full audit of our own code found

27 October 2026 · updated 8 November 2026 · Youngjune Kwon

A tool that asks you to keep your API keys in it should be able to say what it is defending against, what it got wrong, and how you can check. This page is that. It covers an audit of ValetFS v0.1.9 (f8fba82) begun on 8 September 2026, which produced fourteen findings — four of them critical.

Update, 8 November 2026. A second review, by a different reader, found that one of those fixes was incomplete and turned up eight more problems. It is written up below. Fixes are on main and ship in v0.4.0 (tagged 8 November 2026; check the releases page for the signed build); v0.3.1 and earlier still have them.

Fourteen findings, one root

The findings looked unrelated until they were laid out together. Then the shape was obvious: authentication was entirely "do you know the session ID". There was no code anywhere that verified the identity of the controller — the phone holding the secrets. F1, F2b, F4 and F7 are all the same hole wearing different clothes.

That is the comparison worth making against the usual arrangement. A .env file has a simple threat model: anything that can read the disk wins. ValetFS set out to remove the resting copy, and for a while it replaced "can read the disk" with "knows a session ID", which is better but not by as much as the design implied.

A second review, and what it reopened

Twelve days after the first write-up, another AI model was given the public source and asked to find what the first audit missed. It reported nine items. I checked each one against the code before acting on it. Each had a real basis; two were less severe than the reviewer reported, and the severities below are mine. They are listed by how the fix is shipped, not by who found them first.

R1, R2 and R3 are the same root as the first audit — who is the other end of this connection — which is why they were findable in code that had already been through it. R1 and R2 need access to the relay path (a hostile relay, or a stolen vault-role token); they are not "anyone who knows a session ID". That is a smaller group than before and not an empty one.

What is still weak after these fixes, stated so nobody has to find it:

  • R4 is open. Anyone who photographed the pairing QR can still obtain a session token. Once a vault identity is pinned, that token cannot read secrets, but it can replace the app's socket or delete the session.
  • The CLI vault asks you to compare the daemon's fingerprint on first use. If you do not compare it, you are trusting the hub for that one step.
  • When the daemon is started from a connection key (the reverse flow), the app learns the daemon's key from the hub rather than from something it scanned. A hostile hub could substitute its own.

Where the tests are

Several findings were attack shapes rather than bugs, so the fixes carry tests that describe the attack. The repository has 23 Go test files; the ones that matter here are internal/noise/conformance_test.go (handshake conformance), internal/session/transcript_test.go and internal/session/authorized_test.go (session binding and authorisation), internal/hub/relay_test.go (what the relay will and will not forward), and internal/hardening/hardening_linux_test.go.

Release integrity

F11 closed with a SHA256SUMS file covering every artefact, cosign keyless signing, and build provenance. The installer verifies the checksum fail-closed. When cosign is not present it says so plainly rather than implying a check it did not make — a checksum that travelled from the same place as the binary is not a defence against a tampered release. Setting VALETFS_REQUIRE_SIGNATURE=1 turns that into a hard failure.

The limit is worth stating: keyless signing binds to a workflow identity, so an attacker who can change the release workflow can produce signatures that verify.

What this audit is not

It was not independent. It was a line-by-line review conducted by the author, in a working session, with an AI assistant — not a third-party penetration test and not a commissioned security review. ValetFS has had neither.

The second review was not independent either: it was another AI model reading the public source, with the author checking every finding against the code afterwards. Neither round was a third-party penetration test.

So read this page as what it is: the findings are specific, the commits are public and you can read them, and the claim "fourteen findings, four critical, all closed at the time" is checkable by anyone who clones the repository. The claim "this code is secure" is not made here, because nobody outside the project has tried to break it yet.
